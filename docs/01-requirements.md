# 01 需求分析

版本：v0.1；日期：2026-10-29；阶段：需求基线（实现后同步状态说明）。依据为候选人获知的选题要求；本文用项目自己的表达组织实现约束，不附原始试卷或页面。

## 1. 用户与业务问题

主要用户是内容运营人员。其需要处理一批待发布素材，但素材可能缺信息、命中审核规则，或与已有排期冲突。人工处理时容易发生：建议时间被误当作确认时间、重复操作生成多份草稿、保存失败后仍向用户报告成功。

项目提供“检查素材 → 获取可用时段 → 协商冲突 → 保存可追踪草稿”的业务闭环。最终给出每项素材的审核结论、风险原因、原要求、建议时段、待确认项和草稿保存结果。

成功不以输出一段流畅文案衡量，而以业务约束和实际保存状态衡量。

## 2. 范围与明确取舍

### 2.1 必须完成

- CLI 输入结构化 JSON，一次支持 1～3 项素材，按输入顺序处理。
- 使用合成素材元数据、补充资料、审核规则和已有排期。
- 提供素材读取、规则检查、时段查询、草稿保存四项核心工具；增加补充资料读取和草稿查询。
- 实现真实模型驱动的工具调用循环；离线 Mock 用于可复现的流程测试。
- 支持正常、缺信息、规则风险、时段冲突、重复提交和保存失败。
- 提供时间变更的显式确认入口；确认后仍只保存草稿。
- 有界执行、结构化输出、脱敏 Trace、单元测试与真实模型评估。
- 同一仓库交付文档、代码、输入、实际输出、Trace 和测试结果。

### 2.2 本版不做

不做真实发布、视频文件分析、OCR/ASR、真实平台审核接入、界面、线上部署、多 Agent、向量数据库、生产级用户认证和分布式调度。

规则检查基于合成元数据和规则；没有读取真实视频，因此审核结果不得宣称为生产内容审核结论。

### 2.3 产品假设

这些是本项目为缩小范围而明确的设计假设，不是题目额外规定：

| 假设 | 本版定义 |
|---|---|
| 时间 | 仅 Asia/Shanghai；完整日期和带偏移的时间，不接受只有“18:00” |
| 排期资源 | channel + account_id + slot_start_utc |
| 时段粒度 | 整点一小时一个发布容量；每个资源每时段最多一项 |
| 可选时段 | 每天 10:00 至 21:00，窗口终点 22:00 不包含在内 |
| 占位含义 | 草稿内部容量控制，不代表外部平台预约或发布 |
| 待确认草稿 | 不占位，可用性只是查询时快照 |
| 已确认草稿 | 保存成功时在本地排期表占位 |
| 时间调整 | 只能作为建议；超出原授权必须取得与具体草稿版本绑定的确认 |
| 素材顺序 | 输入顺序优先，不做最优批量排程 |
| 规则优先级 | BLOCK 高于缺信息/人工复核，高于 PASS；时间确认不能覆盖审核风险 |

其他时区、半点时段或超出输入数量均明确拒绝，不自动转换成另一项用户意图。

## 3. 输入和信息缺失

最小请求具有 request_id、channel、account_id、timezone 和 items。每个 item 包含 material_id 和发布要求。发布要求有两种：

1. EXACT：指定必须保持的原时间。出现冲突时可以提议其他时间，但不能直接执行变更。
2. WINDOW：用户授权的时间窗口，窗口内选择可用整点不需要额外时间确认；窗口外建议必须待确认。

无发布要求属于业务信息不足，可返回 needs_input。缺 request_id、JSON 无法解析、枚举不合法、格式错误属于输入错误，CLI 在调用模型前拒绝。

素材信息缺失时，模型可选择查补充资料；补查仍缺失则请求补充。程序不通过默认值伪造素材授权、标题或可用日期。

## 4. 必须遵守的业务不变量

| ID | 不变量 | 可检查证据 |
|---|---|---|
| INV-01 | 没有发布能力；任何状态都不等于已发布 | 工具注册表、输出、源代码 |
| INV-02 | 原要求不可被模型覆盖 | 输入指纹、requests 表、最终输出 |
| INV-03 | 未授权改期不能占位 | 确认校验测试、slots 表 |
| INV-04 | 未读取与未检查的素材不能保存可执行排期草稿 | 保存前置条件测试 |
| INV-05 | BLOCK 或人工复核未解决时不能占位 | 规则结果、数据库断言 |
| INV-06 | 同一 request_id + material_id 只有一份草稿 | 唯一约束、跨进程重复测试 |
| INV-07 | 保存成功必须有提交后的数据库记录支持 | 事务测试、readback.json |
| INV-08 | 查询空闲不代表保存时仍空闲 | 保存事务中的再次检查 |
| INV-09 | 工具失败不改变成成功状态 | 错误注入、输出及 Trace |
| INV-10 | 达到上限明确未完成，保留已成功项 | 上限测试、部分完成输出 |
| INV-11 | 模型不能自行创建确认凭据 | 工具参数 Schema、伪造测试 |
| INV-12 | 更换工具事实后重新观察，不重放旧答案 | 变更占用时段后的真实模型运行 |

## 5. 功能需求和验收

| ID | 需求 | 可判定的验收条件 |
|---|---|---|
| FR-01 | 读取素材 | 返回元数据、缺失字段、版本和来源 ID；未知素材有明确错误 |
| FR-02 | 补查信息 | 补充工具只返回已存在的合成资料；无结果不填造 |
| FR-03 | 规则检查 | 输出 rule_id、严重级别、证据字段和可执行建议 |
| FR-04 | 查询时段 | 返回原时段是否占用、候选时段、资源与查询快照版本 |
| FR-05 | 正常排期 | 审核通过且原授权时间空闲，保存一份 reserved 草稿并返回保存成功 |
| FR-06 | 信息不足 | 补查失败后列出缺失字段及需补充问题，不占位 |
| FR-07 | 规则风险 | 硬风险阻断；软风险需人工复核；时间确认不覆盖风险 |
| FR-08 | 时段冲突 | 建议替代时段，保留原要求，标记待确认，不占位 |
| FR-09 | 显式确认 | 确认匹配草稿、版本和建议时间；重新审核与查冲突后才允许占位 |
| FR-10 | 重复提交 | 相同请求多次运行、跨进程重启后仍只有同一草稿 ID |
| FR-11 | 幂等键滥用 | 相同 request_id 携带不同规范化业务输入，拒绝为 IDEMPOTENCY_CONFLICT |
| FR-12 | 保存失败 | 提交前失败：无新记录且明确 failed；提交后响应丢失：查询核实或明确 unknown |
| FR-13 | 新冲突 | 待确认建议时间后来被占用，确认不成功，重新建议也必须重新确认 |
| FR-14 | 动态决策 | 真实模型至少两条路径因不同工具观察而选择不同后续动作 |
| FR-15 | 执行限制 | 计数所有模型请求和工具尝试；超限后不再执行副作用 |
| FR-16 | 批量部分结果 | 已保存项不回滚；未完成项有状态和原因，不整批虚报成功 |
| FR-17 | 可追踪结果 | 每项素材列出审核、风险、时间、确认、保存和任务状态 |

## 6. 状态与“完成”的含义

具体枚举以接口契约为准。以下概念必须分开：

- 审核通过：只是规则层面允许进入排期。
- 建议可用：只是某次查询时空闲。
- 待用户确认：原硬要求尚未被具体授权修改。
- 草稿保存成功：数据库事务提交成功；可能仍是 pending 草稿。
- 已确认并占位的草稿：完成本项目的排期任务；仍未发布。

每项任务仅在审核 PASS、时间属于原授权或有有效确认、reserved 草稿已提交时为 completed。待确认草稿即使成功保存也为 awaiting_confirmation。

批量 run_status：全部 completed 为 completed；至少一项 completed 且并非全部完成为 partial；没有完成项为 incomplete。具体未完成原因保留在每项中。

## 7. 成功标准

### 核心达标

六类必验收场景全部有可执行用例；至少三组实际输入、输出与 Trace 覆盖正常、信息不足、工具失败；真实模型至少两条不同观察路径；达到上限有明确结果；仓库材料齐全且能按命令复现。

### 争取优秀

在核心完成后，再证明：

1. 更换占用时段后，模型改查其他时段，而非坚持旧建议。
2. 待确认草稿更新时保持同一 ID，确认版本变化后旧确认失效。
3. 重复执行和数据库唯一约束在并发/跨进程下均有效。
4. 保存时发生新冲突或响应丢失，不会虚报完成。
5. 真实模型评估报告同时呈现通过、失败、调用量和局限。

“优秀”是本项目的质量目标，不代表对评审分数或录取结果的承诺。

## 8. 待实施验证的问题

- 所选模型能否稳定调用六项工具和结束动作？
- 简短规则描述是否足以减少跳过检查、重复查询和无依据结束？
- 在 24 次模型请求、20 次工具尝试、180 秒整体限制内，三项输入能完成多少？
- 使用多条真实路径重复评估后，确认边界和失败表达是否稳定？

这些问题通过实际测试与运行证据回答，见评估文档；本需求表保留目标，不把目标当作已通过结论。

## 9. 当前实现与需求差距

本地已实现请求校验、六项工具、原生模型循环、Mock/live 适配、SQLite 草稿与确认、执行预算及证据导出。实现不是生产发布系统；公开输出为 dict，严格 Pydantic 模型用于业务输入。当前使用固定 +08:00 代替 zoneinfo，仅覆盖明确限定的上海时区。SQLite 锁等待固定最多 2 秒，没有按剩余总时限动态压缩，因此严格截止时间仍存在最多一次锁等待的边界。测试数、真实模型通过率与未通过项以评估证据为准。GitHub 提交和候选人独立复核不能仅凭代码已生成认定完成。
