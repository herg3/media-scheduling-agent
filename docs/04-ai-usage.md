阶段：需求与开发文档，2026-10-29。本记录只陈述实际发生的事；开发后应继续追加，不把计划写成候选人已完成的工作。

## 1. 已发生的协作

| 环节 | AI 实际辅助 | 候选人已发生的动作 | 验证状态 |
|---|---|---|---|
| 选题比较 | 比较四题的验收风险、实现成本和工程展示价值，推荐选题一 | 提供考核要求，授权技术取舍，确认选题一 | 选题已确认 |
| 需求分析 | 提出范围、业务不变量、六项验收与失败边界 | 要求先写需求和开发文档，强调规范与质量 | 文档供候选人评审 |
| 技术设计 | 提出 Python、原生循环、SQLite、确认和幂等方案 | 尚未记录候选人逐项修改或代码实现 | 设计尚未运行验证 |

| 文档生成 | 编写 README、需求、方案、契约、评估和计划 | 尚未完成候选人最终审阅 | 静态检查与运行验证分开 |
| 工程实现 | 本阶段未生成业务程序 | 未发生 | 未验证 |
| 真实模型评估 | 本阶段未调用业务模型 | 未发生 | 未验证 |

不能将“候选人选择了题目”扩写为“候选人独立设计并实现全部系统”。AI 生成内容须明确标注；候选人的后续阅读、修改与验证分别留证。

## 2. 本阶段使用的辅助方式

通过当前对话中的 Codex 助手进行需求拆解、方案讨论、文档生成及本地文件检查。没有使用子 Agent，没有向第三方发送消息，没有创建 GitHub 远端，没有安装依赖，没有请求或记录真实 API Key。

实际 AI 模型的精确内部版本未从当前界面核实，不编造版本号。项目未来接入的业务模型与辅助编程工具是两个不同记录项。

## 3. 主要设计建议及待验证内容

| AI 建议 | 候选人需要理解或验证的内容 |
|---|---|
| 原要求、建议、确认、保存分离 | 为什么 pending 保存成功仍不是任务完成 |
| request_id 与唯一约束 | 同键不同输入为什么应拒绝；跨进程如何防重 |
| 确认与版本绑定 | 为什么确认19:00不能授权20:00 |
| 保存事务重新检查冲突 | 为什么查到空闲后仍可能保存失败 |
| 输出依据事实台账 | 为什么不能直接相信模型自报 saved |
| Mock 与 live 分开统计 | 为什么离线测试通过不代表模型会正确决策 |

以上是理解和验证目标，不是对候选人已经掌握的声明。

## 4. 开发期间追加记录方式

每次有实质改变时追加一行：

| 日期/提交 | 问题或需求 | AI 参与范围 | 候选人实际修改 | 验证命令和结果 |
|---|---|---|---|---|
| 本阶段 | 需求和设计准备 | 文档起草与核对 | 确认选题、提出质量要求；其他修改尚未记录 | 业务测试未运行 |

开发完成后至少记录一次具体的“发现问题 → 修改 → 重新验证”。若实测没有发生对应修改，保留真实过程，不人为编造学习故事。

## 5. 候选人接手检查

- 能从一个输入手动追踪到数据库草稿和 Trace。
- 能解释六项工具各自的输入、结果和可能错误。
- 能改一个占用时段并复现模型动作变化。
- 能注入一次保存失败，并解释输出和数据库结果。
- 能说明一次自己实际做出的修改及其验证命令。

这些检查未执行前，不在提交说明中写“已独立复现”。
