# 02 技术方案与设计取舍

状态：设计，未实现。输入输出的字段、枚举、工具和错误码以 [07-contracts.md](07-contracts.md) 为准；验收以 [03-evaluation.md](03-evaluation.md) 为准。

## 1. 技术选择

| 选择 | 采用原因 | 代价与约束 |
|---|---|---|
| Python 3.12 | 工具函数、JSON、CLI 和测试实现直接 | 当前默认 Python 3.9.21，需先建立目标环境 |
| 原生单 Agent 循环 | 模型动作、观察与副作用容易检查；不额外引入框架状态抽象 | 自行处理消息关联、Schema、预算与日志 |
| Pydantic 2 系列 | 校验请求、动作和输出 | 开发时锁定确切版本，不能只写“最新版” |
| httpx | 封装一个经验证支持工具调用的模型接口 | 兼容 API 不等于所有模型行为兼容 |
| SQLite | 单机持久化、唯一约束和事务足够覆盖本题 | 单写者；不宣称分布式或生产容量 |
| 标准库 argparse / zoneinfo | 减少 CLI 依赖，明确时区 | Windows 显式依赖 tzdata |
| pytest | 断言状态、调用、错误恢复和数据库结果 | 离线测试不能替代真实模型评估 |

开发时同时锁定运行依赖和测试依赖，记录 Python、SQLite、模型 ID、提供方及依赖版本。当前不指定一个未经本机验证的模型型号，也不默认任何服务端都支持相同参数。

比较过的替代方案：LangGraph 适合复杂恢复和持久工作流，本题暂不需要；全条件分支实现便于测试，但无法独立满足模型动态决策要求。采用原生循环，保留以后替换模型适配器的边界。

## 3. 模型循环与程序门禁

每轮模型接收：用户目标、原始限制、工具描述、此前 assistant 工具调用与对应 tool 结果。其返回一项工具动作，或 finish 结束动作。

1. 检查总时限、模型调用预算。
2. 请求模型；该请求计入模型步数，即使失败。
3. 验证动作格式、工具名和参数；一次只执行一个动作。
4. 检查工具预算；尝试、参数拒绝、重试均计入工具次数。
5. 调用工具，将结构化观察加入消息和事实台账。
6. 再次由模型决定补查、替代查询、保存、请求确认或停止。
7. finish 或预算耗尽时，程序按台账与数据库事实构建输出。

模型原文不直接决定 saved、confirmed 或 reserved。它可以提出建议和简短决策说明，但这些字段由工具结果及提交后的状态生成。

模型一次返回多个工具调用时，不执行其中任何副作用，为各调用返回协议错误并允许一次修正。累计两次非法模型响应后结束为 failed；所有尝试仍受全局上限约束。

不保存模型内部思维过程。只记录对用户有意义的简短动作依据，例如“原时段占用，查询同日其他候选”；若模型未提供该说明，记录缺失，不由测试脚本伪造为模型表述。

## 4. 动态决策与确定性代码的分工

| 模型决定 | 程序负责 |
|---|---|
| 先查什么、是否补查 | 工具可访问范围和参数校验 |
| 冲突后查哪段候选、建议哪个时段 | 候选是否真实、是否在允许时段 |
| 观察错误后重试、查询核实或停止 | 预算、可重试次数、幂等 |
| 信息不足时问什么 | 不允许凭空补齐事实 |
| 是否提交草稿、是否结束 | 保存前审核、确认、事务与真实状态 |

例如程序检查“没有用户确认就不能为变更后的时间占位”属于必要的业务门禁；若程序提前写死“冲突后必选 19:00”，模型仅润色结果，则不满足本项目决策设计。

至少两条真实路径应能定位到：不同观察 → 模型不同动作 → 对应工具结果或未完成原因。

## 5. 审核与资料边界

素材读取返回版本、来源、元数据和缺失项；补充资料按 material_id 查询，与主资料一起形成规范化的素材视图。合并顺序由程序确定，冲突字段返回显式资料冲突，不让模型擅自覆盖。

规则检查工具自己读取规范化视图，模型不能传一份“已审核通过”的元数据替代真实资料。规则按规则文件版本执行，返回 rule_id 和事实字段：

- 缺少必要授权：needs_information，可尝试补查。
- 确定禁用内容或明确授权过期：blocked。
- 需要人工判断的措辞：needs_review，本版不能通过时间确认解除。
- 没有命中：pass。

BLOCK 始终优先。风险或资料不足时不保存排期草稿；结果保留可操作的问题和风险原因。此取舍减少“风险草稿被误执行”的歧义。

## 6. 时段与确认

时段只表示整点发布容量，不使用视频长度作为占位时长。所有时间解析为 UTC 存储，展示保留 Asia/Shanghai。

EXACT 的原时段空闲时，原输入已授权该时间，可保存 reserved 草稿。WINDOW 内同理。超出原授权的建议只能保存 pending 草稿，不写入 slots。

用户通过 confirm 命令明确确认 draft_id、revision、proposed_at。CLI 根据已有草稿生成运行期可信确认上下文，模型工具参数中不存在 confirmed=true 或任意确认凭据入口。

确认绑定：request_id、material_id、draft_id、revision、proposal_hash、具体 proposed_at。任何建议时间或审核事实版本变化均使旧确认无效；新的有效建议需要新的用户确认。

确认动作触发同一 Agent 再运行并重新读取素材、规则和时段。确认本身不保证成功；若时间已被占用，保存返回 SLOT_CONFLICT，模型可建议新时间，但新时间仍待确认。

CLI 操作视为本地操作者授权，不构成生产身份验证。不能宣称“已确认用户身份”。

## 7. 幂等、修订与新事实

### 请求登记

request_id 是用户提供的稳定业务请求号。程序对规范化业务输入计算 request_fingerprint：相同 ID 同指纹允许重跑；同 ID 不同业务输入拒绝。忽略模型后端、Trace 输出目录和测试故障等非业务参数。

### 草稿唯一性

drafts 对 request_id + material_id 建唯一约束。重复执行不会新增第二份草稿，重启进程后同样适用。

对同一草稿：

- 内容及 proposal_hash 一致：返回 already_exists 和同一 draft_id。
- pending 草稿需要修改建议：必须带 expected_revision，乐观检查后更新同一行并增加版本。
- reserved 草稿不能被模型自动改期；需要用户新业务请求，且本版不实现取消/迁移旧占位。
- 相同素材在相同账号下另建请求时，已有 reserved 草稿也阻止重复排期。

重复请求不直接命中“最终答案缓存”。每轮读取最新素材、规则和占用情况，以识别旧建议失效。已有 pending 建议从 19:00 改为 20:00 后保持草稿 ID，版本和 proposal_hash 改变，旧确认失效。

## 8. 保存事务

保存前验证当前运行确实读取、审核过该素材并查询过候选时间；最终保存仍重新读取当前数据，避免模型绕过或使用过期观察。

SQLite 写入采用短事务：

1. BEGIN IMMEDIATE；读取已有草稿和版本。
2. 重读当前素材与规则，校验来源版本及建议的有效性；授权期限必须覆盖 proposed_at，而不仅是当前时钟。
3. 判断原授权或可信确认；pending 不占位，reserved 必须有授权。
4. 对 pending 和 reserved 都校验候选时段当前仍空闲；pending 只保存建议，reserved 额外写入独占资源键。
5. 插入或更新同一草稿，提交。
6. 提交后读回并返回真实 draft_id、revision、reservation_status。

不在事务中等待模型或网络。SQLite 的单写者机制意味着锁争用需要显式处理；唯一约束承担最终防重，不能只靠“先查后写”。这些基础行为依据 [SQLite 事务文档](https://www.sqlite.org/lang_transaction.html) 与 [约束文档](https://www.sqlite.org/lang_createtable.html)。

pending 保存时空闲也不保证之后持续空闲；其不占位，用户确认时必须再次检查。查询曾经空闲但保存时已被占用的建议，不能当作“可用建议”写入。

已知失败分两类：

- 明确提交前失败：回滚，返回 failed。
- 已提交但响应丢失：返回 unknown；模型可通过 get_draft 核实。读回存在才可报告 saved；读回也失败则保持 unknown，不声称回滚或成功。

## 9. 错误、预算与部分结果

默认全局上限：24 次模型请求、20 次工具尝试、180 秒。任何一个先达到就停止新动作，已成功保存的草稿保留。未完成项标记 incomplete，说明 MODEL_STEP_LIMIT、TOOL_CALL_LIMIT 或 DEADLINE_EXCEEDED。

每次模型请求超时不超过 30 秒，并受剩余全局时间限制。SQLite 等待不超过 2 秒，且不能超过剩余时间。模型网络失败无自动后台重试，报告 MODEL_UNAVAILABLE；业务工具瞬时失败可由模型决定有限重试，同一工具同参数最多尝试两次。

计算同参数重试次数时忽略 decision_summary 等日志字段，按工具名、素材、时间范围和 expected_revision 等业务参数形成计数键；防止模型仅改解释文字就绕过次数限制。

达到时限前已提交的写入不能因为后续模型超时被称为未保存；输出按事实分列“保存成功”与“总体未完成”。deadline 检查在每次副作用前及返回后执行。

批量中一个素材受阻不会删除其他素材成功结果。不可恢复的数据库/模型故障结束当前运行，其余素材标记未完成。

## 10. 证据与真实模型接入

真实适配器把工具定义发给模型，将带 tool_call_id 的观察回传下一轮。官方 [Function Calling 文档](https://help.aliyun.com/zh/model-studio/qwen-function-calling) 描述了此交互方式；本项目是否兼容某个具体接口必须在开发时实测。

离线 Mock 根据当前消息和观察返回工具动作，仅用于测试循环、门禁和故障路径，不能冒充模型推理效果。backend=live 不可用时不自动降级为 mock。

Trace 至少记录 run_id、backend、模型标识、输入指纹、资料版本、步骤、动作、参数、观察摘要、后续动作与简短依据。测试用例和预期路径不放进真实模型上下文。

为证明工程控制有效，另用不可信 FakeModel 尝试跳过审核、伪造确认、伪报保存成功。这些是门禁测试，不作为真实模型表现记录。

## 11. 文档和证据的可信边界

本方案是待实施设计，不是运行结论。技术参考用于核对接口和数据库行为，没有搜索或公开考题。代码完成后，根据实际实现同步本文；不保留与代码不一致的“理想设计”。

尚未验证：模型稳定性、确切依赖版本、真实调用费用、跨进程竞争结果及全部运行命令。
