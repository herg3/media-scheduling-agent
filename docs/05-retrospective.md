# 05 阶段复盘与后续改进

阶段：文档设计。以下内容为本轮 AI 协助分析形成的认识，不是候选人实施后的个人复盘；真实开发完成后按实际经历修订。

## 1. 当前最难的问题

### 状态之间容易混淆

“审核通过”“时间空闲”“用户同意”“保存成功”是不同事实。若只设置一个 success 字段，就可能把保存了待确认建议描述为排期完成。方案因此分开审核、确认、占位和保存状态，并限定 completed 的条件。

尚待验证：最终输出构建器能否在模型错误表述时仍保持这些边界。

### 模型应当有决策空间，程序仍须控制业务权限

题目需要模型根据观察改变动作；把所有分支写死不能证明这一点。但把确认和保存状态交给模型自报，又会引入越权和虚假成功。

当前取舍是模型选择工具与结束时机，程序限制确认权限、证据和数据库写入。尚待真实 Trace 证明模型并非只沿固定路径运行。

### 幂等不能使旧建议一直有效

重复提交需要防重，但占用数据可能变化。如果直接缓存第一次答案，会在时段改变后返回过期建议。因此同请求重跑仍观察事实，pending 草稿可在版本检查下修订，保持同一 ID。

尚待验证：变更占用、并发修订及旧确认失效是否正确。

### 保存响应丢失不等于保存失败

提交前失败可明确回滚；提交后响应丢失需要查询核实。当前设计保留 unknown，避免错误宣称成功或失败。此项作为核心路径完成后的恢复能力补强。

## 2. 本轮获得的设计认识

- 优秀的交付需要可检查的数据库事实与运行记录，文案不能替代。
- 本地元数据规则可以证明流程约束，不能证明真实视频审核能力。
- SQLite 的事务和唯一约束可以控制本题单机写入，不能自动推出分布式正确性。
- 离线 Mock 的可复现性与真实模型的决策表现必须分开验证。
- Windows 时区数据需要显式处理，不能只依赖默认系统环境。

这些认识基于设计分析和官方资料，没有冒充实测结论。

## 3. 开发后应回答的问题

| 问题 | 需要的实际证据 |
|---|---|
| 模型最常在哪一步出错？ | 失败 Trace、次数、后续修改 |
| 哪项门禁拦截了错误动作？ | FakeModel 测试和数据库断言 |
| 修改提示词是否改善效果？ | 相同用例、相同版本条件下的前后试次 |
| 哪项设计最终被简化？ | 实际代码、原因和剩余限制 |
| 候选人亲自改了什么？ | 提交差异、运行命令、验证结果 |

没有对应证据就保持“尚未回答”，不补写虚构结果。

## 4. 改进优先级

1. 首先完成六项验收、真实模型循环、执行上限与可复现证据。
2. 再补确认后新冲突、占用变化重跑、跨进程幂等和保存未知恢复。
3. 之后根据真实失败数据改善工具说明、错误恢复和提示词。
4. 若业务扩展，再考虑持久化中断恢复、真实平台资源同步、取消/迁移排期和生产授权。

当前不计划用界面、多 Agent 或更多框架替代核心验证。
