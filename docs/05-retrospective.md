# 05 实际开发复盘

更新：2026-10-29。本复盘是AI协作实现和实测过程的记录，候选人的个人学习与修改仍需本人补充。

## 最难的问题：把历史保存与当前任务分开

最初工具上下文只有last_save与last_error。一次保存成功后，如果模型尝试另一个未查询时间并失败，旧last_save可能继续使结果completed。另一个问题是SAVE_OUTCOME_UNKNOWN可能被后续查询错误覆盖。普通正常测试发现不了这些组合。

代码审查用不可信FakeModel和真实SQLite复现问题后，引入独立save_error、is_current及版本比对。保存失败保留历史draft_id，但不表示新建议成功；unknown必须经get_draft核实才能解除。最后一次存储读回不可用时，已核实提交的快照仍保留，同时明确警告。

这次修改说明：Agent不能只有“最后一条消息”或“最后一个错误”，必须区分事实的来源、适用范围和发生顺序。

## 模型决策与用户确认

真实模型曾在EXACT原时段占用时直接请求用户泛泛改期，没有查询替代并保存草稿。程序安全地返回未完成，但产品目标没有达成。

原因是“不得擅自改硬要求”与“可保存待确认建议”没有说明得足够清楚。提示词补充pending不占位、不改变原要求，允许先查询并保存建议，确认是后续动作。仍由模型选择查询范围、工具与停止时机，没有写死18冲突就改19的代码路径。

修改前的失败Trace保留，修改后用相同类场景重新评估，结果见03-evaluation。不能把低温度当绝对确定性或一次成功当稳定保证。

## 测试本身也可能错

最初E09用固定19:00作为新冲突。但模型可能建议10:00，之后确认10:00确实合法，测试却断言“不该成功”。这不是越权发布，而是故障未注入目标时段。

评估器改为读取第一轮实际草稿时间，再占用该时间；changes.json记录前后状态。允许模型面对新冲突合理重新建议或停止，检查无越权占位、原要求和确认边界，而非只接受固定工具顺序。

## 工程取舍与计划变化

- 使用已安装Python3.13.14，源代码最低3.12；没有另外安装解释器。
- 原生工具循环足以展示动作、观察和边界，无需多Agent业务架构。编程时的子Agent仅为开发协作。
- 输出采用可审阅dict和确定性构建器；请求使用Pydantic严格校验，不夸称全输出Schema已实现。
- 用固定+08:00处理本版唯一时区，tzdata保留为依赖；没有声称已实现多时区/DST。
- SQLite唯一约束、短事务和重查满足单机考核；不推出分布式或生产正确性。
- 锁等待固定2秒，并非完全受剩余deadline动态约束，已记录限制。
